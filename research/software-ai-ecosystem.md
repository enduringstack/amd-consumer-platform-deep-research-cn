# 软件与 AI 生态：ROCm、HIP、Ryzen AI Software、Windows 与 Linux

## 1. 硬件能力只有被软件命中才存在

AMD 平台同时有 CPU、RDNA GPU、CDNA GPU 和 XDNA NPU，开发者面对的不是一条统一执行路径。CPU 由成熟 x86 编译器和操作系统调度；Radeon 图形走 DirectX/Vulkan/OpenGL；GPU 计算走 ROCm/HIP、OpenCL 或框架后端；NPU 需要 Ryzen AI Software、ONNX 图编译与系统 API。一个模型可能把不同节点分到三种设备。

软件生态分析应分五层：内核驱动与固件；用户态运行时；数学/媒体/通信库；框架和模型；应用与运维。安装成功只证明前两层部分工作，跑出一次结果不证明数值正确、性能稳定或升级可维护。支持矩阵是产品合同，比论坛成功截图更可靠。

## 2. ROCm 的组件边界

ROCm 是开源 GPU 计算平台总称，包含 amdgpu 内核接口、KFD/HSA 运行时、HIP 编译与运行时、rocBLAS/hipBLASLt、MIOpen、RCCL、rocFFT、rocRAND、分析器和调试器等。[A037][A043] 不同发行版本并非所有组件同号，容器还会复用宿主内核驱动。

Instinct 是 ROCm 的首要验证对象。官方兼容矩阵按 MI 系列、Linux 发行版、内核、虚拟化和 ROCm 版本列支持。[A038] 生产部署应从矩阵选择组合，而不是先装最新包再找能否运行。操作系统小版本升级可能更换内核，影响 DKMS/驱动；容器不能绕过宿主驱动不兼容。

Radeon/Ryzen 有独立文档与矩阵，因为显示和计算共用 GPU，Windows/Linux 驱动模型也不同。[A039] 快照日 Windows 表将设备分为 Runtime 与 HIP SDK 支持，部分数学库仅 Linux 提供。某张卡能运行 HIP kernel，不等于 PyTorch、FlashAttention、量化库或专业应用都获得官方支持。

版本冻结建议使用机器可读清单：GPU PCI ID/gfx target、VBIOS、主板 BIOS、内核、amdgpu、ROCm、Python、框架、容器镜像、模型 commit 与编译参数。升级时保留旧环境，先跑单元正确性、确定性、性能和长时稳定，再切生产。

## 3. HIP：源代码可移植性的实际含义

HIP 是 C++ 运行时 API 与 kernel 语言，可在 AMD 平台由 HIP-Clang 编译，也可面向 NVIDIA 后端。[A040] 它提供与 CUDA 相近的线程、块、内存和流概念，使大量 kernel 可机械转换。hipify 工具能替换 API 名，但不能自动处理所有语义和性能。

迁移难点包括：CUDA 专有库、内联 PTX、warp=32 假设、未定义竞争、不同原子/同步、共享内存大小、寄存器压力、编译器扩展和驱动行为。AMD wavefront 可能是 32 或 64，算法若硬编码掩码会错误。正确做法是用 HIP 的可移植原语和库，运行跨后端测试。

性能可移植比功能可移植更难。一个 tile 尺寸在 NVIDIA SM 上最佳，可能在 AMD CU 上因 wave、LDS、寄存器和缓存不同而降低占用。库调用如 GEMM 应优先交给 hipBLASLt，而不是维护自写内核；自定义热点再按架构调优并保留通用路径。

二进制插件是更硬的边界。只发布 CUDA cubin 的 Python wheel 不能由 HIP 直接运行，必须有源码和构建系统。选择 AI 工具前查 wheel 是否包含 ROCm 版本、支持哪些 gfx target；“Python 项目”不表示底层没有 CUDA-only 扩展。

## 4. 框架：PyTorch、TensorFlow 与上层生态

PyTorch ROCm 构建尽量保持相同 Python API，设备字符串有时仍显示 `cuda` 以兼容现有代码。这只是 API 选择，不代表实际使用 NVIDIA。诊断需查看 PyTorch 版本、ROCm 构建标记和设备名称，而不是字符串。

框架发布节奏与 ROCm 不完全同步。官方容器通常锁定经过验证的组合，社区 nightly 可能支持新 GPU但回归风险更高。生产用户选择稳定镜像，消费新卡用户可能必须等待正式 wheel或用 TheRock/源码构建；应清楚标为社区可用而非官方支持。

模型生态的瓶颈常在自定义 attention、量化和推理引擎。主干算子由框架支持不保证扩展支持 AMD。部署前列出模型依赖的 Triton、FlashAttention、bitsandbytes、vLLM、llama.cpp 等具体后端，逐一核验版本。回退到通用 kernel 可能正确但速度显著下降。

数值正确性必须独立验证。FP16/BF16/FP8 舍入、融合顺序和原子非确定性会导致差异。设置容差前先比较任务指标，不以“能生成文字”代替 logits 或训练收敛验证。低精度峰值只有在模型缩放和校准保持质量时才有价值。

## 5. RCCL 与多 GPU

RCCL 提供 all-reduce、all-gather、reduce-scatter、broadcast 等集合通信，框架分布式训练通过后端调用。性能取决于 GPU 拓扑、PCIe/Infinity Fabric、NIC、消息大小、算法和 rank 放置。单 GPU kernel 快不能保证多 GPU 扩展。

节点内先验证 P2P 矩阵和每链路单向/双向带宽，再跑集合基准；跨节点先测 NIC 与 GPU 亲和、RDMA 和网络拥塞。总线带宽与算法带宽口径不同，不能直接与端口速率比较。小消息由启动延迟主导，大消息才接近带宽。

环境变量可用于诊断和选算法，但随机复制“性能魔法参数”会掩盖拓扑或驱动问题。每项变量记录原因、默认值、适用版本和回滚。超时应先查某 rank 崩溃、网络丢包或 collective 顺序不一致，而不是无限增大 timeout。

## 6. Windows GPU 计算

Windows 消费生态的优势是应用和驱动整合，限制是 ROCm/HIP 组件覆盖较 Linux 窄。快照日官方 Windows 表明确 RX 9000、部分 RX 7000、Radeon PRO 和 Ryzen AI Max 支持层级，也明确一些 RDNA 2 卡只有 Runtime 而没有完整 HIP SDK。[A039] 用户必须以当期表为准。

DirectML 是微软的低层机器学习 API，运行在 DirectX 12 设备上，允许 Windows 应用跨供应商 GPU。[A044] 它降低厂商专用部署门槛，却不保证所有模型都有同等优化。Windows ML/ONNX Runtime 执行提供者可能选择 DirectML、NPU 或 CPU，应用需暴露设备和回退信息。

WSL 提供 Linux 用户态体验，但 GPU 驱动通过 Windows 主机映射，不等于原生 Linux。文件系统跨边界、网络、容器和内核功能有差异。重训练或高 I/O 任务应比较原生 Linux，交互开发可用 WSL 简化工具。支持表必须点名 WSL 和 GPU。

Adrenalin 驱动同时服务显示、游戏、媒体和部分计算。[A049] 生产 AI 与每日游戏共用机器时，驱动升级可能造成冲突。可为稳定任务保留容器/环境和旧安装包，更新前导出配置。Windows Update 也可能替换驱动，应纳入变更控制。

## 7. Linux 图形与计算栈

Linux amdgpu 是内核驱动，文档覆盖显示、内存管理、调度、RAS 和调试接口。[A050] 用户态图形通常使用 Mesa，ROCm 使用自己的计算组件；发行版内核、Mesa 与 ROCm 可来自不同渠道。版本错配是黑屏、设备未枚举或计算失败的重要来源。

消费桌面优先发行版集成图形栈，除非 ROCm 文档要求特定驱动。随意混装 AMDGPU-PRO、发行版 Mesa 和 ROCm 包可能覆盖库。安装前用包管理器和容器规划，失败后不要用复制单个 `.so` 的方式永久修补。

权限包括 `/dev/kfd`、`render` 组和容器设备映射。把容器设为 privileged 虽能绕过问题，却扩大攻击面；应只映射需要的设备和组。多用户工作站还要限制性能计数器和显存访问，防止侧信道或数据残留。

Linux 新硬件 enablement 可能依赖新内核和固件。XDNA 驱动在 AMD GitHub 开源，发行版合入和用户态支持有时间差。[A045] 自己编译驱动适合开发验证，不应被描述为普通用户正式可用。

## 8. Ryzen AI Software：NPU 部署流水线

Ryzen AI Software 提供模型量化、编译、运行时和示例，用于 XDNA NPU。[A041] 典型流程是从 ONNX 模型开始，规范输入形状，量化到支持精度，编译为设备图，在运行时提交张量。每一步都可能因算子、动态形状或精度失败。

图划分是性能核心。NPU 支持的连续子图越大，设备切换越少；不支持节点回退 CPU/GPU会带来同步和内存转换。开发者应读取编译报告，列出落在 NPU 的节点比例，并用端到端时延而非子图 kernel 时间评价。

量化需要代表数据校准。图像、语音和语言模型对量化误差敏感度不同，单个样例正确不能证明质量。应保留 FP32/BF16 基线、任务指标和每层误差，必要时混合精度。NPU TOPS 的价值要乘以算子覆盖和利用率。

官方 RyzenAI-SW 仓库包含示例和发布信息，可用于锁定代码与 issue。[A042] GitHub main 分支不是稳定发布，生产应使用 tag/commit。示例支持的模型不代表任意变体，输入大小、opset 和权重仍需匹配。

## 9. CPU、GPU、NPU 的任务分配

CPU 适合控制流、低批量、tokenization、数据库和不规则算子；GPU 适合大并行、图形、训练与较大模型；NPU 适合受支持、持续、低功耗推理。最佳设备由端到端能量和时延决定，不由 TOPS 排名。

小模型一次推理可能在 CPU 更快，因为无需编译和设备提交；摄像头持续滤镜适合 NPU，因为长时间低功耗；大语言模型权重读取适合宽内存 GPU；训练通常用 GPU。混合执行要减少跨设备边界，让每段包含足够工作摊销。

调度还要考虑用户体验。前台游戏占 GPU 时，把助手推理放 NPU可避免帧率争用；视频会议占 NPU 时，LLM 可能转 GPU/CPU。系统应提供优先级、取消和功耗模式，不以所有单元同时 100% 为目标。

## 10. 本地大模型：容量、后端与可复现

本地 LLM 需要权重容量、KV cache、内存带宽和受支持 kernel。模型参数量乘每参数字节只估权重，不含量化表、运行时、缓存和系统。长上下文与并发会让 KV cache 成为主导。Ryzen AI Max 的大共享内存可容纳更大模型，性能仍由 LPDDR 带宽和后端决定。

llama.cpp 一类项目可能通过 HIP、Vulkan 或 CPU运行。不同后端的算子覆盖、量化格式和图卸载不同；报告 token/s 必须记录模型精确文件、量化、上下文、batch、提示长度、生成长度、后端 commit、线程和功耗。首 token 延迟与稳态生成速率分开。

“70B 可运行”不是产品结论：极低量化可能影响质量，全模型装入但只生成 1 token/s 也未必实用。对话助手应同时测首 token、20–50 token/s 目标、长上下文和系统响应；编码助手还要测 prompt ingest 与工具调用。

隐私要看应用数据流。本地权重可能仍调用在线认证、更新、遥测或搜索。敏感部署用防火墙/抓包验证，检查模型许可证和缓存位置。NPU/GPU 不自动提供机密计算。

## 11. 图形软件：DirectX、Vulkan 与 GPUOpen

Windows 游戏主要通过 DirectX 12，跨平台和 Linux/Android 使用 Vulkan，旧应用仍有 DX11/OpenGL。驱动要编译着色器、管理显存和调度队列；首次着色器编译可造成卡顿，游戏或驱动缓存能改善。评测应区分首次运行和热缓存。

GPUOpen 汇集 AMD 的开放图形 SDK、性能工具和文章。[A046] Radeon GPU Profiler、GPU Detective 等可分析波前、缓存、崩溃与帧。开放源码利于跨 GPU 采用，但开发者整合和测试决定游戏是否交付。

FidelityFX SDK 提供 CAS、SSSR、降噪、超分和其他组件。[A046] 组件是源代码/库，不是驱动全局自动优化。游戏选择版本、输入缓冲和 UI 处理；不同实现质量会不同。FSR 支持多厂商是覆盖优势，机器学习版本可能要求特定硬件路径。

FSR 的渲染比例、帧生成和延迟要分开。超分从低内部分辨率重建，帧生成插入中间帧，不提高游戏逻辑或输入采样；基础帧率过低时插帧画面更流畅但交互仍慢。比较 DLSS/XeSS 必须同输出分辨率、质量档、基础帧和锐化。[A048]

## 12. 媒体、创作与应用认证

Radeon/Ryzen 媒体引擎支持 H.264/H.265/AV1 等具体编解码路径，但编码质量、色深和应用接口随代际。直播测试要用相同码率、预设和场景比较画质；导出要确认应用真正调用硬件，而非 CPU fallback。

DaVinci Resolve、Adobe、Blender、CAD 等有各自后端和插件。硬件支持 OpenCL/HIP 不代表应用启用；专业版本、驱动认证和 OS 也会改变。选购前以软件供应商支持页和实际项目验证，避免仅依 AMD 峰值。

Radeon PRO 的认证驱动减少特定版本组合的风险，RX 驱动更新更快服务游戏。创作者可在 RX 获得高性价比，但生产稳定性要自行承担。混合使用显示和长计算时，Windows TDR、桌面响应与显存抢占需测试。

## 13. 编译、调试和性能分析

CPU 侧使用 GCC/Clang/MSVC 与 perf、uProf、VTune 类工具；GPU 侧用 rocprofiler、rocTracer、Omniperf/rocprof、Radeon GPU Profiler；NPU 用编译报告和运行时 trace。工具名称随版本变化，结论应保留版本。

性能优化流程是先建立正确基线，再定位热点，再一次改变一个变量。GPU 看 kernel 时间、占用、wave、LDS、寄存器、缓存和传输；CPU 看 IPC、分支、缓存、NUMA；NPU看图覆盖与设备边界。只看利用率百分比无法区分满算与等待。

编译缓存和 JIT 会污染首轮。报告冷启动与热运行；模型编译时间与部署推理分开。动态形状可能产生多个编译变体，占磁盘与启动时间。生产服务应预热并设缓存生命周期。

## 14. 驱动可靠性与回归管理

驱动故障可能来自内核、用户态、固件、应用、超频、电源或硬件。排查先恢复默认时钟和内存，检查系统日志/AER，最小化应用，再更换已知稳定驱动。清洁安装是工具，不是对所有问题的解释。

游戏驱动按新作快速更新，ROCm 稳定版按验证周期发布，OEM 笔记本又可能要求定制包。用户在 AMD 通用驱动与 OEM 驱动间选择时，应保留恢复介质；混合显卡/MUX、电源和热键可能依赖 OEM 组件。

回归测试集合应覆盖设备枚举、显示/休眠、典型游戏、媒体、AI 正确性、长时计算和多 GPU。只跑一个 benchmark 无法发现待机功耗或视频问题。记录 known-good 状态，升级失败能回滚。

## 15. 安全与隔离

GPU/NPU 可处理敏感提示、图像和模型。多用户环境需要设备权限、容器隔离、显存清理、固件签名和 IOMMU。把 `/dev/kfd` 暴露给容器相当于授予设备访问，应限制可信工作负载。

AMD PRO、EPYC 的安全功能包括安全启动、内存加密和虚拟化能力，但具体功能依 SKU/平台。[A078] 加密会有性能和运维取舍，密钥、证明和固件更新仍需平台方案。消费 Ryzen 的安全标签不能直接替代企业威胁模型。

AI 供应链包括模型文件、Python 包、容器和编译器。校验哈希、固定依赖、扫描镜像和最小权限比“完全离线”口号更重要。社区 wheel 可能包含预编译本机代码，应从可信发布源获取。

## 16. 开源战略的优势与边界

ROCm、GPUOpen 和 XDNA 驱动开放，使开发者能查看实现、提交补丁并支持 Linux。对云和研究客户，开放编译器和内核降低黑盒风险；对游戏开发者，跨厂商 SDK 扩大采用。

开源不等于成熟、完整或无需支持。issue 数、PR 合并速度、文档一致和二进制发行才决定体验。某组件开源而固件或验证闭源仍可形成依赖。企业需要 SLA 和责任边界，不能把社区热情当服务合同。

AMD 的挑战是减少多入口碎片：Instinct ROCm 文档、Radeon/Ryzen ROCm、Ryzen AI Software、GPUOpen、Vitis/Vivado 分属不同受众。统一安装、版本语义、硬件发现和诊断能显著降低采用成本，比再增加一个峰值指标更有价值。

## 17. 与 CUDA、oneAPI、Metal/MLX 和 Qualcomm 栈比较

NVIDIA CUDA 的优势是长期库、工具、应用和人才，硬件/软件垂直优化；代价是供应商锁定。AMD HIP 试图降低 CUDA 源迁移并以开放 ROCm竞争，硬件容量常有吸引力，但长尾扩展和 Windows 覆盖需逐项查。[A072]

Intel oneAPI/SYCL 强调跨 CPU/GPU/加速器，Core Ultra 也组合 CPU、GPU、NPU。[A069] AMD 与 Intel 都面对 x86 OEM 多样性和驱动矩阵；差异应落到具体应用、GPU 规模与软件版本，不能用厂商口号。

Apple 控制 M 系列 SoC、统一内存、macOS、Metal/Core ML/MLX 与整机，端到端一致性强，但内存购买后不可升级、平台封闭。[A070] Ryzen AI Max 在共享内存容量和 x86 软件上形成竞争，仍依赖多 OEM 与 Windows/Linux。

Qualcomm Snapdragon X 以 Arm、集成 NPU 和 Windows on Arm 争取能效。[A071] 原生 Arm 应用可表现良好，x86 转译和外设驱动是变量。AMD 的 x86 兼容降低迁移，却要在待机和整机协同上竞争。

## 18. 端侧 AI 验收方法

第一阶段验证可用性：驱动识别设备，目标模型能编译，所有算子有明确放置。第二阶段验证正确性：与 CPU 高精度基线比较任务指标。第三阶段验证性能：冷启动、首结果、稳态吞吐、长上下文和并发。第四阶段验证能效与体验：墙上/电池能量、温度、噪声、前台响应。

测试矩阵至少包含 CPU、GPU、NPU 三条路径以及自动调度。自动路径可能因版本变化，记录日志。模型名称必须带版本/哈希、量化、上下文和输入；硬件带 SKU、RAM、功耗；软件带 OS、BIOS、驱动和运行时。

若 NPU 只覆盖部分图，报告覆盖比例和 CPU fallback 时间；若 GPU 借用共享内存，报告系统剩余和带宽；若设备过热，报告稳定段而非首轮。没有这些条件的 TOPS/倍数只能放在产品规格，不进入体验结论。

## 19. 面向不同用户的软件建议

普通消费者优先 OEM 稳定驱动和应用功能，不为 NPU 手动安装开发栈。游戏玩家维护一个稳定 Adrenalin 版本，更新前查游戏修复；创作者查应用认证和媒体路径；本地 AI 爱好者选择官方矩阵点名的 GPU/APU，使用固定容器或 Python 环境。

开发者优先框架标准 API 和库，隔离厂商专用优化；CI 至少跑 CPU 与一条 AMD GPU/NPU 路径。企业冻结全栈、维护 SBOM 和回滚，使用官方支持；集群运维把通信、固件与容器一起升级。

真正的“生态成熟”不是 demo 数量，而是从安装、正确、性能、诊断、升级到恢复都可预测。AMD 已有覆盖 CPU、GPU、NPU 的主要组件，下一阶段价值取决于能否让支持矩阵更宽、更一致、更容易被应用默认选择。
