# AMD 平台实验手册：持续性能、端侧 AI、兼容性与故障定位

## 1. 实验目标与最小可复现单元

实验不是为了制造一个总分，而是回答可执行问题：某台机器能否在规定噪声和功耗下完成任务；换内存、驱动或模型后差异来自哪里；连续运行是否稳定；升级能否回滚。每项实验写一个假设和反例，例如“模型受内存带宽限制”，反例是提高内存带宽后速度不变且算力利用上升。

最小记录包括设备精确 SKU、主板/整机型号和 revision、BIOS/AGESA、内存容量/通道/速率、GPU VBIOS与驱动、存储、OS build、内核、功耗模式、室温、应用/模型 commit、命令和原始输出。缺任何关键项，结果只能作为观察，不能跨系统推广。

重复至少三次，区分冷启动与热缓存。报告中位数、范围和异常原因，不只报最好一次。长时实验先热浸再取稳态。自动更新、杀毒、索引和遥测可能干扰，记录而非随意关闭；若关闭，结果代表实验环境而非默认用户体验。

## 2. 基线快照

硬件层在 Linux用 `lscpu`、`lspci -nnvv`、`dmidecode`、`numactl -H`、`rocminfo` 等，在 Windows用系统信息、设备管理器、GPU-Z/HWiNFO类可信工具和 PowerShell。保存文本，不只截图。核对核心/线程、缓存、NUMA、PCIe速率宽度、内存通道、gfx target与 NPU。

固件层记录 BIOS所有非默认项：EXPO、PBO、Curve Optimizer、Resizable BAR、Above 4G、IOMMU、虚拟化、CPPC、风扇。开始时加载 optimized defaults，再只启用任务必需项。OEM控制中心模式也保存。

软件层导出包和驱动版本。ROCm用 `rocminfo`/包管理器，框架打印 build和设备；Ryzen AI记录运行时、模型编译器；游戏记录 build、着色器缓存状态。官方支持矩阵是可用性基准。[A037][A039]

## 3. CPU 单线程实验

单线程测试覆盖前端、分支、整数、浮点和内存，不用一个综合分。选择真实任务：代码编译单文件、压缩单线程、浏览器脚本、音频或某科学 kernel。合成 microbenchmark只用于解释端口/缓存，不作为体验。

记录有效时钟而非请求时钟，查看核心是否迁移。Windows调度可能在 CCD间移动，Linux可用 taskset稳定但应同时测默认。固定核心能揭示硬件，默认调度代表用户。最大 boost是短时上限，报告全程频率分布。

Zen 5宽前端在分支可预测、ILP足够时获益；指针链仍受延迟。使用硬件计数器看 cycles、instructions、branches、misses、L1/L2/L3与 DRAM。IPC高低不能跨不同指令比较，完成时间是主指标。[A023]

## 4. CPU 多线程与扩展

从1、2、4、8线程逐步到全部物理核和 SMT，绘制速度提升与效率。理想线性很少，串行比例、锁、内存和频率下降会弯曲。超过物理核后 SMT收益依空闲执行资源，可能为正、零或负。

编译、渲染和压缩分别代表依赖图、浮点和内存。Threadripper测试要扩到不同 CCD/NUMA，检查线程是否跨域。高核心数若每核带宽不足，速度平台期；增加 DIMM通道或改善数据布局比更多线程有效。

记录封装功耗、温度和稳态频率。PBO能提高功耗换性能，Eco Mode降低功耗可能提高每瓦。比较默认与 Eco时以完成任务能量评估。对生产机器，稳定与噪声是约束，不以最高分自动获胜。

## 5. 缓存和 3D V-Cache 实验

用不同工作集大小做延迟/带宽阶梯，观察 L1/L2/L3/DRAM边界。随机指针链测延迟，顺序多流测带宽，两者不要混。预取会让顺序访问看起来快，这是实际能力而非作弊，但不代表随机。

比较 X3D与非 X3D须对齐核心、频率、内存和功耗，难以完全对齐时明确。游戏选择 CPU限制场景，同时测4K GPU限制作为反例。生产任务选择数据库、编译、仿真和渲染，避免只选有利样本。[A029]

双 CCD X3D记录线程落点。可用每 CCD计数器或限制 affinity做诊断，再测默认调度。若绑到缓存 CCD提升，问题可能是识别；若默认最好，手工优化无必要。升级 Windows/驱动后重测。

## 6. DDR/LPDDR 内存实验

带宽测试含读、写、复制和多线程；延迟含本地与跨 NUMA。内存超频比较保持 CPU功耗和任务相同，记录 UCLK/FCLK比例与时序。标称 MT/s提升但控制器分频时，延迟可能上升。

稳定性不能只跑短 MemTest。使用多种模式、接近满容量、CPU+GPU共享、睡眠和冷启动。错误计数哪怕很少也不可接受，尤其编译/压缩校验。EXPO属于超频，失败时回默认不是性能倒退而是正确诊断。

APU iGPU测试单双通道/不同 LPDDR速率，记录 GPU频率和功耗，区分带宽墙与功耗墙。若 GPU频率相同而内存带宽上升带来帧率，说明供数；若封装功耗满，CPU/GPU争用需单独测试。

## 7. GPU 光栅实验

选择至少三类游戏：电竞高帧、现代开放世界、重着色/高分辨率。固定版本、场景、画质、分辨率、API和着色器缓存。优先内置可复现 benchmark，再用固定路径采集；多人在线不适合精确对比。

报告平均、1% low、0.1% low或完整帧时间分布，注明采集长度。平均高但周期尖峰会体感卡顿。首次运行与热缓存分开，驱动更新后清缓存可测编译体验。CPU限制时记录 GPU利用和频率。

功耗测整卡/墙上，记录 TBP、热点、显存温度、风扇和噪声。AIB卡比较默认 BIOS，不混厂商 OC。降压要做多游戏和长时，单 benchmark稳定不够。

## 8. 光追、超分与帧生成

光追按相同 RT效果、分辨率和无超分基线比较，再分别开启 FSR/DLSS/XeSS。不同质量档内部渲染比例可能不同，应记录。截图用相同帧/运动场景，观察细线、透明、粒子、鬼影和闪烁。

帧生成报告基础 FPS、输出 FPS和输入延迟。若基础 30插到60，画面更新数增加但游戏逻辑和输入仍接近30，伪影概率高。使用延迟测量或高帧摄像，不能由输出 FPS推断响应。

FSR 4依游戏集成和支持硬件，官方页面确认技术范围，具体质量由版本。[A048] 驱动级覆盖若存在，也需区别原生。不要把一个游戏的结果推广全部 RX 9000。

## 9. 显存容量与 PCIe 溢出

逐级提高纹理、分辨率、光追和资产，记录显存占用、驻留、PCIe流量和帧时间。当分配接近容量时，观察是否突然尖峰。监控工具的“已分配”不等于物理使用，结合驱动预算。

比较8/16/24GB卡时尽量同 GPU，否则算力混淆。可用创作项目或模型控制容量。PCIe 4/5和 x8/x16差异在容量内可能小，溢出后增大。Resizable BAR分别开关并逐游戏验证。[A054]

APU共享内存没有独立显存硬边界，却可能把系统推向 swap。记录总 RAM、GPU分配和 page faults。把共享内存机器描述为“96GB显存”会忽略系统保留，报告“GPU可用共享内存上限与条件”。

## 10. 媒体实验

编码测试固定源视频、分辨率、帧率、色深、码率、GOP和预设。比较速度、VMAF/SSIM与人工画质，文件大小一致才公平。直播加入场景变化、文字和高速运动；测丢帧和音画同步。

解码测试4K/8K、AV1/H.265、HDR和多流，记录 CPU/GPU占用、掉帧与功耗。浏览器是否调用硬解由 codec和 DRM决定。外接屏色深/HDR链也验证。

剪辑导出同时测试 timeline交互、特效和最终输出。应用可能在不同效果用 CPU/GPU，日志或性能图确认。Radeon支持某编解码不保证插件调用。

## 11. NPU 模型编译与正确性

选择公开可重复模型，固定 ONNX opset、输入和权重 hash。先在 CPU高精度运行，保存输出和任务指标。按 Ryzen AI Software流程量化/编译，保存报告，列出 NPU子图、CPU fallback和不支持算子。[A041][A042]

分类模型测 top-1/任务数据集，检测测 mAP，语音测 WER，生成模型用任务指标与人工样本。不要只比单张图。量化校准集需代表生产分布，偏差会让硬件看似快但质量不可用。

性能分冷编译、冷启动、预热后单请求、批量和持续。NPU目标通常小批低功耗，强行大 batch追 TOPS可能不符合端侧。记录 CPU前后处理，端到端才是应用时延。

## 12. CPU/GPU/NPU 横向调度实验

同一模型在 CPU、GPU、NPU用相同输入与精度尽量对齐；若后端不支持相同精度，明确质量差异。测时延、吞吐、能量、峰值内存和前台响应。结果不是决定一个永久赢家，而是建立任务调度规则。

测混合负载：视频会议 NPU+浏览器 CPU、游戏 GPU+语音 NPU、本地 LLM GPU+编译 CPU。记录封装功耗和内存争用。单设备最快的后端在混合任务中可能伤害前台，应考虑优先级。

自动调度在驱动/应用升级后可能改变，使用 trace确认。若系统把模型回退 CPU，结果不能记作 NPU性能。应用应暴露后端选择与失败原因。

## 13. 本地 LLM 实验

记录模型全名、权重 hash、参数量、量化方法与位宽、上下文、batch、线程、GPU offload层、后端版本。提示分为短问答、长文摄入和多轮，分别报告 prompt processing与 generation token/s、首 token和峰值内存。

验证输出质量。不同量化用固定评测集或任务成功率，不能只展示一段看似合理文字。温度和采样参数固定。模型版本不同的速度/质量不可归因硬件。

Ryzen AI Max重点测试共享内存容量曲线：模型从完全驻留到接近上限，再到触发换页。观察 token/s和尾延迟。与独显比较同模型量化和功耗，独显容量不足时报告分层方案，不把失败排除。

持续一小时观察内存泄漏、热、频率和上下文增长。并发测1/2/4用户，吞吐和尾延迟权衡。交互助手更看首 token，批处理看总吞吐。

## 14. ROCm 安装与支持验证

先从矩阵选硬件/OS/版本，不从安装教程倒推支持。[A038] 保存发行版、内核、驱动和 ROCm包。安装后运行设备枚举、简单 HIP、库 GEMM、框架 tensor，再跑目标应用，逐层定位。

容器记录镜像 digest，映射 `/dev/kfd`和 render设备，验证用户组。容器看到 GPU不表示库 target包含该 gfx。检查 kernel code object。避免用不受支持环境变量覆盖 gfx作为长期方案，它可能产生错误结果。

Windows区分 Runtime与 HIP SDK，某些库 Linux-only。[A039] WSL和原生路径分别测。新消费 GPU社区启用可以探索，但报告标为非正式，生产建议等待官方。

## 15. HIP 移植实验

建立 CUDA基线的正确输出与性能。用 hipify转换，先求编译和正确，再分析热点。列出无法转换的库、PTX、warp假设和扩展。每项替换写测试，避免一次改大块后无法定位。

使用 HIP API的设备属性而不是硬编码 wave/warp，采用 cooperative groups或库原语。对 reduce/scan等优先 rocPRIM/hipCUB。GEMM用库并搜索调优。源可移植后，在 NVIDIA和 AMD CI同时运行。[A040]

性能调优观察 occupancy不是越高越好，寄存器/LDS减少可能增加访存。扫描 tile、工作组和向量宽度，保留每架构配置。对比相同精度和算法，不让一个后端启用 Tensor Core而另一个用标量。

## 16. 多 GPU 与通信实验

绘制 `lspci -tv`/rocm topology，标出 GPU、CPU、NIC。先做每对 GPU P2P可用、单向/双向带宽和延迟。再跑集合通信不同消息大小、rank顺序和线程。总线带宽口径注明。

跨节点先验证普通网络、MTU、丢包，再 RDMA/GPUDirect路径。NIC与 GPU绑同 NUMA，CPU通信线程也靠近。用单对流确认峰值，再全节点暴露拥塞。交换机缓冲、ECN/PFC或 IB配置由网络团队记录。

应用扩展效率等于单卡时间除 N卡时间再除 N。低效率可能来自通信、数据加载、负载不平衡或小 batch。Profiler分解，不直接怪 RCCL。失败注入拔掉进程/端口，验证超时和恢复，不让作业无限挂。

## 17. 存储与数据加载

NVMe测试顺序、随机、不同队列深度、持续写和温度。厂商峰值通常高 QD，桌面加载可能低 QD。文件系统、加密和压缩按实际开启。测试数据大于 RAM避免全由页缓存。

AI训练监控 GPU空闲等待 DataLoader。增加 worker、预取、固定内存和数据格式，观察 CPU与存储；过多 worker会争内存。图像解码可在 CPU/GPU，比较总能量。

游戏加载记录首次、重复、着色器编译和网络。SSD更快若 CPU解压限制，加载变化小。模型加载包括反序列化和量化转换，也不能只看磁盘读。

## 18. 续航和能效实验

电池先校准健康与实际容量。固定亮度（用亮度计）、刷新、无线、音量和电源模式。办公脚本应包含网页、视频、文档和空闲，记录每阶段；连续视频仅代表解码。

任务能量用 Wh或积分功率，报告完成时间。插电墙上功率减空闲基线可估增量；笔记本用电池放电更接近移动。充电时不要测放电，电池温度影响。

比较 Eco/平衡/性能模式，寻找性能/瓦甜点。掌机按多个 TDP点绘制 FPS/W，而不是只测最大。NPU与 CPU/GPU同任务也以质量相同的焦耳比较。

## 19. 热浸、噪声与可靠性

热浸至少到温度和时钟稳定，通常30–60分钟；大型机架更久。记录室温，温升比绝对温度可跨日比较。CPU/GPU混合比单项最能加热机箱。SSD、VRM和内存温度也看。

噪声在固定距离和背景测 dBA，同时记录频谱/主观音调。风扇周期波动可能平均分贝不高但恼人。修改曲线后验证温度和部件寿命，不让 VRM/SSD失去气流。

长时可靠性用重复实际任务、内存和 GPU压力，监控 WHEA、AER、MCE、amdgpu reset和应用校验。压力软件可能产生不现实功耗，只作为边界，实际任务决定稳定。

## 20. Windows/Linux 双平台兼容

同硬件双系统比较前对齐 BIOS和功耗，应用编译器/驱动差异如实保留。Windows游戏和专业插件可能更完整，Linux开发/ROCm可能更完整。不能把不同 API性能当纯 OS开销。

测试睡眠、外屏、音频、Wi-Fi、蓝牙和 USB，而非只算力。新 APU Linux enablement可能需新内核；Windows OEM驱动可能落后通用版。记录哪些路径正式支持，哪些社区修补。

文件共享注意 NTFS Fast Startup和权限，模型/数据 hash验证。双系统时间和 Secure Boot配置记录。系统更新后跑冒烟集合。

## 21. 虚拟化与容器

CPU虚拟机测试嵌套、IOMMU、NUMA和内存；vCPU不要跨太多 CCD。GPU直通需要独立 IOMMU组、VBIOS和 reset支持，消费 GPU不保证企业级 SR-IOV。成功一次重启不等于可长期重置。

容器隔离用户态但共享内核驱动。镜像 ROCm版本必须与宿主兼容。限制内存/CPU/GPU可见性，记录 cgroup。多租户消费 Radeon缺硬分区，不应用容器声称安全隔离。

WSL2是虚拟化路径，文件放 Linux虚拟磁盘通常比跨 `/mnt/c`大量小文件快。GPU由 Windows驱动映射，兼容按官方 WSL矩阵。性能差异需用相同文件位置和版本解释。

## 22. 安全功能实验

验证 Secure Boot状态、TPM、磁盘加密、固件密码和恢复。更新 BIOS后确认 BitLocker，不把关闭安全作为永久性能调优。企业管理测试远程资产、更新和擦除，具体 PRO/OEM支持为准。[A078]

虚拟化内存加密/机密计算在 EPYC上需 hypervisor与 guest支持，测启动、证明和性能。GPU/DPU是否进入信任边界需架构文档，不因 CPU加密就假定 DMA设备数据全保护。

模型供应链保存签名/hash、依赖 SBOM与容器扫描。离线推理用网络监控确认无外发。敏感提示日志和崩溃转储也要清理。

## 23. 故障定位树：无法启动

新装 AM5无启动：确认 CPU供电、内存插槽、BIOS支持和诊断灯；第一次 DDR5训练可较久，不反复断电。用单条 QVL内存、核显/最少设备、默认 BIOS。需要时用明确文件与步骤 Flashback。

升级后不开机：清 CMOS会删除 EXPO/PBO；保留 BitLocker密钥。若旧 CPU可用，确认 BIOS确实刷新。检查针脚/插槽和散热压力。不要在未知状态连续盲刷不同 BIOS。

GPU无显示：确认线插独显/核显、供电、插槽和显示器输入，尝试低速/另一端口。Above4G/ReBAR先默认。若系统已进 OS，用远程或核显查驱动。

## 24. 故障定位树：随机重启与驱动超时

先恢复 CPU/GPU/内存默认，检查 PSU接头、墙插和温度。读取 WHEA/AER/系统日志，区分电源瞬断、CPU机器检查、GPU reset和应用崩溃。没有蓝屏的关机常指供电，但仍需证据。

内存不稳可表现 GPU超时，因为 GPU从错误系统内存读取。运行内存校验；独显显存错误另测。更换驱动前保存日志。若只一个游戏失败，查游戏和着色器；所有 GPU负载失败再看硬件/驱动。

笔记本 OEM模式和 MUX切换会触重启/黑屏，使用支持路径。eGPU问题分热插拔、链路、线缆和电源。不要用提高电压作为第一修复。

## 25. 故障定位树：ROCm/NPU 不工作

ROCm：矩阵是否点名 GPU/OS；`lspci`与内核是否识别；用户是否有设备权限；`rocminfo`是否列 agent；框架是否为 ROCm构建；gfx target是否包含。逐层，勿一开始重装系统。

若简单 HIP工作而框架失败，问题在用户态版本/扩展；若框架基本 tensor工作而模型失败，列 unsupported op或 CUDA-only模块。性能低用 profiler确认 CPU fallback和传输。

NPU：设备管理器/xdna枚举、运行时版本、模型编译、算子覆盖、应用执行提供者。应用显示“AI”不保证 NPU。保存编译/运行日志，检查是否转 CPU。OEM固件和 Windows build按官方要求。

## 26. 结果解释的统计纪律

硬件 benchmark噪声来自温度、后台、随机调度和场景。三次很接近可报告中位，差异小于测量变异就写“无可辨差异”，不强行排序。必要时增加样本和置信区间。

多个游戏求几何平均可描述比例，但会掩盖兼容问题。附每游戏结果和异常，样本选择提前定义，避免看到结果后挑。厂商测试若选择不同游戏，不能直接对比平均。

回归阈值根据任务：性能下降3%可能在噪声内，正确性错误任何比例不可接受，尾延迟增加20%对交互严重。预先写门槛，减少确认偏差。

## 27. 报告模板

标题写问题；摘要写结论和适用边界；环境用表；方法给命令/场景；结果保存原始 CSV和图；分析用计数器解释；限制列未控制变量；附复现步骤和来源。不要截断不利结果。

产品宣称单独一栏，注明 AMD测试条件；自己的结果不写成“官方”。若引用产品规格，使用来源 ID。动态价格写日期和地区，不纳入长期技术结论。

数据文件用 ISO日期和 git commit，脚本版本控制。敏感序列号、用户名、token在公开前扫描。原始日志可压缩发布，个人信息脱敏。

## 28. 代表工作负载套件

消费桌面：浏览器、Office类、代码编译、压缩、目标游戏、视频转码、待机。创作：时间线、RAW、Blender、音频低延迟。AI PC：视频会议 NPU、图像/语音、LLM。掌机：多个 TDP、休眠、五款游戏。

工作站：全核渲染、编译扩展、内存带宽、多 NVMe、多 GPU、认证应用。服务器：NUMA、虚拟化、网络、数据库、功耗。AI：单 GPU kernel、模型训练/推理、多 GPU/节点、checkpoint和故障。

套件不需覆盖所有 benchmark，要覆盖购买任务和瓶颈类型。每季度保留相同核心集合评估驱动回归，新应用作为补充而非替换历史。

## 29. 从实验到决策

先检查硬约束是否全部满足，再对稳定结果加权。若两个平台性能接近，选择内存余量、噪声、服务和迁移成本更好者。若 AMD硬件领先但应用不支持，记录等待条件和替代后端，不用未来承诺补分。

为选择写失效条件：模型超过内存、软件停止支持、工作负载转 CUDA-only、功耗预算改变、OEM固件结束。达到条件就重评。这样购买不是品牌忠诚，而是可管理假设。

最终可复现证据应该允许另一个人指出错误。保留环境、原始数据和失败，才能区分 Zen/RDNA/XDNA的真实特征、OEM实现和偶然噪声。深度分析的完成标准不是最长报告，而是每个重要结论都有下一步验证方法。
